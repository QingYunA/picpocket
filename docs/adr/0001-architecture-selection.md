# 0001: 架构选型：MV3 + SidePanel + IndexedDB + 纯前端 BYOK

## 状态
已通过 (Accepted)

## 上下文与问题陈述
在开发一款用于收集网页图片灵感并由多模态 AI 反推绘图 Prompt 的 Chrome 扩展时，需要解决以下核心诉求与冲突：
1. **常驻与低干扰**：用户在多网页漫游找灵感时，传统 Popup 弹窗会在点击网页空白处时自动销毁，打断浏览连续性；新建独立 Tab 标签页则带来频繁切屏成本。
2. **海量图片本地存储容量**：扩展内存储几十到上百张高质量原图与缩略图时，`chrome.storage.local` 默认配额仅 10MB 且大对象序列化极慢。
3. **数据隐私与云端运营成本**：若由开发者搭建私有后端服务代发 Vision API，将面临高昂的并发带宽/Token 成本、服务器运维压力，以及用户对私密图片上传中转的隐私信任危机。

## 决策 (Decision)
我们决定采用以下组合架构方案：

1. **容器形式**：基于 Chrome 114+ 原生 `chrome.sidePanel` API 构建持久化侧边栏。侧边栏与当前网页并排显示，支持跨标签页状态保持。
2. **离线存储**：采用浏览器原生 **IndexedDB**（结合 `Dexie.js` 驱动），用于存储原图 Blob 二进制数据、压缩缩略图以及结构化元数据；仅把少量轻量设置（如 API Key、选中模型偏好）存入 `chrome.storage.local`。
3. **网络与 AI 架构**：采用 **纯前端直连（BYOK - Bring Your Own Key）** 模式。
   - 依赖 Chrome 扩展 MV3 声明的宿主权限直接在客户端向各大模型服务商（Google Gemini、OpenAI、Ollama 本地服务等）发起安全 HTTPS 请求。
   - 绝不架设中间转发服务器，保证 API Key 与图片资产 100% 留在用户本地，实现零服务端运营成本与极致隐私安全。

## 后果 (Consequences)

### 正向影响
- 极佳的用户操作心流：边刷网页边收集，侧边栏随时待命。
- 零后端开销：项目可完全以纯静态客户端扩展形式开源发布，无服务器账单压力。
- 隐私完全自主：用户无需担忧图片被第三方抓取或泄露。
- 容量充沛：IndexedDB 在现代 Chrome 中提供数 GB 级别的离线存储上限。

### 负向与妥协
- 用户需要自行获取并配置 Gemini 或 OpenAI 的 API Key（门槛略高于开箱即用的付费 SaaS，但对极客与创作者更透明可靠）。
- Chrome Side Panel 宽度相对受限（通常约 360px ~ 420px），UI 必须进行高密度的紧凑布局设计。
